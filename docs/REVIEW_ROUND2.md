## 三、二次检查：又发现了什么

### 3.1 本轮中当场发现并修掉的

**500 时请求 ID 全是 `-`。**
第一版把 ID 放在 `@app.middleware("http")` 里，但 500 响应其实由**更外层**的
`ServerErrorMiddleware` 生成，压根没经过我们的中间件，于是响应头和异常日志里都是 `-`。
验证脚本第一版还误判通过（`-` 也是非空字符串）。
修法：中间件自己接住未捕获异常生成 500 响应，ID 与日志就对得上了；
异常 handler 里再加一层兜底，拿不到 ID 就现生成一个。
修完实测：`X-Request-ID: c622a57c`，与日志里的 ID 一致。

### 3.2 第 1 轮点名的 P0-2 —— 已补修（用户授权后）

**硬超时不杀线程**：`_run_with_timeout` 原来用 `with ThreadPoolExecutor(...)`，
`result(timeout=)` 超时后 `__exit__` 会 `shutdown(wait=True)` 阻塞等线程结束，
而卡住的正是 `mcp_stdio` 里无超时的 `stdout.readline()`。
结果是"超时"只让主线程先抛错，接口照样挂到子进程结束。

修法两处：
1. `_run_with_timeout` 换成 **daemon 线程 + 超时后主动掐断上游**（`cancel` 回调），不再用会阻塞等待的线程池。
2. 三种 MCP 传输各加 `abort_active()`：stdio 强杀子进程、SSE 关闭事件流、WebSocket 关底层 socket。
   管道/流一断，阻塞的读操作立刻返回，工作线程才真能退出。

实测（假 MCP 读请求但永不回复，`MCP_TIMEOUT=3`）：

```
HTTP 504 耗时 8.0s
body: {"status":"error","error_code":"MCP_TIMEOUT","message":"MCP服务暂时不可用（检索超时（>8s））…"}
```

并且服务进程能干净退出（不再被卡住的线程拖住）。改之前这个场景是**无限期挂起**。

### 3.2.1 新暴露的现场风险：arXiv 会封 IP（重要）

真模型端到端那次，`warnings` 里出现：

```
来源 MCP 不可用：HTTP 406 from export.arxiv.org
来源 arXiv  不可用：HTTP 406 from export.arxiv.org
来源 Semantic Scholar 不可用：HTTP 429
```

也就是说**主源全挂，最后是靠 Crossref 兜底才拿到 5 篇**。Crossref 质量最差（README 自己写了
"常返回书籍章节、摘要为空"），报告基于它生成，就是项目自己明令禁止的"基于垃圾输入的自信输出"。

排查结论：**是 IP 级封禁，不是 UA 或频率问题。** 间隔 5 秒重试仍 406；
换 5 种 UA（含浏览器 UA、带邮箱的规范 UA）全部 406；加 `Accept: application/atom+xml` 也无效。
触发原因就是我们这段时间反复压测 arXiv（官方建议请求间隔 3 秒）。

**演示前必须做的三件事：**

1. **演示前 1 小时不要反复跑 arXiv**，让它冷却。
2. 提前跑一次要演示的主题，把结果**缓存住**（`CACHE_TTL` 临时调到 3600），现场即使 arXiv 被封也能秒回真实结果。
3. 备选源：去申请一个免费的 **Semantic Scholar API key**，配进 `MCP_HEADERS` 或作为第二源——
   它现在返回 429 是因为没 key 的匿名配额太低。

### 3.2.2 兜底：新增 OpenAlex 源

因为 arXiv 封禁不可控，加了一个不依赖任何密钥的兜底源 `backend/sources/openalex.py`，
并把它放进默认降级顺序（`mcp,arxiv,openalex,crossref`，你的 `.env` 已改）。
OpenAlex 免费、无需 key、限流宽松，摘要是倒排索引，代码里翻回正常文本。

实测对比（同一主题"图神经网络"，arXiv 406 期间）：

| 兜底源 | 结果 |
|---|---|
| Crossref（原来的兜底） | 5 篇，质量差，容易是水刊/书籍章节 |
| OpenAlex（现在） | 5 篇，头一条是 GNN 奠基论文 *The Graph Neural Network Model*（Scarselli 2008，被引 9738） |

加上它之后，同样的请求 `warnings` 里不再出现 Crossref 与 Semantic Scholar 的失败，报告 overview 从 180 字变 260 字。

### 3.2.3 自建 MCP Server 加了 `search_openalex` 工具

arXiv 封禁还有个副作用：自建 MCP Server 里的 `search_arxiv` 打的也是 arXiv，必然失败，
"我们走 MCP 协议调论文工具"这个演示卖点会当场掉链子。

给 `scripts/local_paper_mcp_server.py` 加了 `search_openalex` 工具，并把 `.env` 的
`MCP_TOOL_NAME` 从 `search_arxiv` 改成 `search_openalex`。

效果：**MCP 链路首次尝试就成功**，`warnings` 里只剩一条翻译提示、不再有任何"来源不可用"告警，
页面干净、耗时 7.3s、报告 262 字。既保住了"真的走 MCP 协议"这个卖点，又能拿到高质量论文。

等 arXiv 恢复后，把 `MCP_TOOL_NAME` 改回 `search_arxiv`（或留空自动挑）即可。

### 3.3 新观察到、但没动（都不阻塞交付）

1. **缓存没有手动清除入口**：想强制刷新只能改 TTL 或重启。可加一个 `POST /api/cache/clear`（0.2 天）。
2. **缓存命中率、当前条数没暴露**：health 里只有 `cache_enabled`，排障想知道缓存有没有在工作，只能翻日志。
3. **缓存键只有 `keyword + limit`**：不含来源与模型配置。影响很小（改配置要重启，重启后缓存自然空），但多实例部署时会不一致。
4. **单源 `PAPER_SOURCE=mcp` 时空结果不降级**，与 auto 模式行为不一致（auto 会继续试下一个源）。
5. **仍然零单元测试**：本轮加的是"验证脚本"，能证明改动生效，但不是回归网。`_to_year`、`_sanitize`、`match_map`、`extract_items`、缓存、错误码这些纯函数最该有 pytest。
6. **`docs/contract/` 里 `success_real.json` 与 `success_arxiv.json` 内容重叠**，样例有点冗余，交付前可清掉一个。
7. **`settings` 与缓存都是模块级单例**，改配置必须重启，测试时没法注入。
8. **没有并发上限**：多人同时点会同时发起多个检索 + 多个模型调用，演示时如果评委几个人一起试，可能把 LLM 额度瞬间打满。

## 四、从"能演示"到"稳定产品"还差什么

先给结论：当前状态是**能演示的原型**（主链路跑通、契约稳定、降级正确、不伪造成功）。
距离"稳定产品"大约 **15–25 人天**；距离"9-26 能交付比赛的 Demo"大约 **1–2 人天**。

### 分级说明

| 层级 | 含义 | 还需投入 |
|---|---|---|
| L1 演示稳 | 评委现场点不会挂、不会转圈不返回 | **0.5 天** |
| L2 可交付 | 队员3 能一键部署，出问题能定位 | +3–5 人天（累计 4–6） |
| L3 稳定产品 | 外人连续用一周不崩、成本可控、可回归 | +8–12 人天（累计 12–18） |
| L4 规模与体验 | 多用户、流式、历史记录、可运营 | +5–7 人天（累计 17–25） |

### 清单

**L1 — 演示稳（0.5 天，强烈建议 9-26 前做掉）**

| 事项 | 人天 |
|---|---|
| 修 P0-2：超时真杀线程（`shutdown(wait=False)` + 给 `readline` 套超时） | 0.3 |
| 演示前把 `LLM_TIMEOUT` 收到 45、跑一次真模型端到端 | 0.2 |

**L2 — 可交付（3–5 人天）**

| 事项 | 为什么 | 人天 |
|---|---|---|
| pytest 单元测试（纯函数 + 缓存 + 错误码） | 现在改一行代码没有任何东西会报警 | 1.0 |
| 契约一致性测试（拿 `docs/contract/*.json` 断言字段） | 防止有人偷偷改字段名 | 0.5 |
| Dockerfile / docker-compose | 队员3 部署不依赖"某台能跑的电脑" | 0.5 |
| 启动自检（缺 `LLM_API_KEY` 时明确报错而不是运行时炸） | 部署排障第一道防线 | 0.3 |
| 日志落盘 + 轮转 | 现场出问题时能事后复盘 | 0.5 |
| health 探活下游（arXiv/模型端点是否可达） | 出问题能一眼看出是哪一环 | 0.5 |
| 接口鉴权（简单 API Key）+ CORS 收窄 | 现在任何人拿到地址都能烧你的模型额度 | 0.5 |
| 数据来源署名与使用条款说明 | arXiv / Crossref 都有使用条款，答辩也可能被问 | 0.3 |

**L3 — 稳定产品（8–12 人天）**

| 事项 | 为什么 | 人天 |
|---|---|---|
| 指标埋点：延迟分布、成功率、缓存命中率、上游失败率 | 没有数据就无法判断"稳不稳" | 1.0 |
| 限流（按 IP/Key）+ 模型调用预算/熔断 | 成本控制，防刷 | 1.0 |
| 上游重试与退避（尤其 S2 的 429） | 现在一次 429 就直接降级 | 0.5 |
| 并发上限（信号量） | 防止瞬时打满上游和额度 | 0.5 |
| 缓存持久化（Redis）或至少跨进程共享 | 多实例时缓存不一致 | 1.0–2.0 |
| 历史持久化（SQLite/PG）：报告可复用、可回溯 | 产品要有"我的研究记录" | 1.5–2.0 |
| 结果排序与去重（跨源合并、按相关性/年份/引用） | 现在完全依赖源的顺序 | 1.0 |
| 提示词注入防护（keyword 清洗） | 用户输入直接进提示词 | 0.5 |
| 配置依赖注入化（`settings` 单例 → 可注入） | 测试与多环境的前提 | 0.5–1.0 |
| CI（push 就跑测试 + ruff） | 三人协作不互相踩 | 0.5 |
| 引用可追溯增强（DOI、引用数、原文快照） | 学术类产品的基本盘 | 0.5 |

**L4 — 规模与体验（5–7 人天）**

| 事项 | 为什么 | 人天 |
|---|---|---|
| SSE 流式接口（"已找到 N 篇"→"正在生成报告"分段返回） | 现在前端只能靠猜时间切换文案 | 1.5–2.0 |
| 请求可取消 | 用户点了不该还继续烧钱 | 0.5 |
| 报告局部重生成（只重算某个主题簇） | 用户反馈"这段不对"时的最小修复路径 | 1.0 |
| 多轮追问（基于已检索论文继续问） | 从"一次性报告"到"导航助手" | 2.0 |
| 优雅关闭、滚动重启不丢请求 | 线上运维基本要求 | 0.5 |

### 一句话总结

> 现在这套代码**赢在取舍正确**：契约收敛、反假成功、依赖极简、降级正确，这四条是比赛评分最看重的。
> 它缺的不是功能，而是**"坏了能知道、能定位、能恢复"**那一整套工程设施——
> 也就是 L2/L3 里那些日志、测试、限流、部署、成本的东西。
> 那些东西对拿奖没有直接加分，但对"能不能真的给别人用"是决定性的。
